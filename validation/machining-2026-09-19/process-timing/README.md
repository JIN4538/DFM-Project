# 작업자 기동시간 관측과 시간 제한 시험 보강

측정일: 2026-09-19, Windows, Python 3.12.14, 프로젝트 `.venv/Scripts/python.exe`.

## 기존 실행의 증거

- `../regression.xml`: `tests_v3/test_processes.py` 18개가 모두 통과했다.
- `../regression-final.txt`와 XML: 전체 회귀 777 통과·2 실패. 두 실패는 1.5초/0.6초 제한 뒤 부모 준비 파일이 없다는 전제 검사였다. 기대한 `TimeoutExpired`는 발생했다. 뒤의 지연 출력 부재 검사는 준비 전제 실패 때문에 실행되지 않았다.
- `../process-isolated-retest.txt`: 해당 파일 단독 실행도 14 통과·4 실패. 준비 파일 부재 3개와 0.4초 제한 전에 flush 출력을 관측하지 못한 1개였다. 따라서 전체 회귀의 부하만을 원인으로 확정하지 않는다.
- 실패 디렉터리를 이후 읽기 전용으로 확인했을 때 원래 지연 출력 파일은 없었다. 준비 표식도 없었으므로, 이 사실만으로 자식 Python 실행 후 정리를 충분히 검증했다고 주장하지 않는다.

## 추가 계측

원시 출력은 `startup-probes.txt`에 보존했다. 각 probe는 기존 `run_bounded([sys.executable, '-c', worker], cwd=Path.cwd(), timeout=10)`를 호출했다. 5회씩 순차 실행했으며 총 10회 모두 종료 코드 0, 예상 stdout, 빈 stderr였다.

첫 5회 worker는 `print('ready', flush=True)`였다. 함수 호출부터 종료·정리까지는 0.791956, 1.538019, 1.508940, 1.509346, 1.496135초였다. 이 값만으로 기동 지연과 종료 정리 지연을 구분하지 않는다.

다음 5회 worker는 `import time; print('ready ' + repr(time.perf_counter()), flush=True)`였다. 같은 Windows 성능 카운터 기준으로 함수 호출 직전부터 첫 출력문의 시간값 생성까지 0.752985, 1.515239, 1.470231, 1.496315, 1.471775초였다. 이후 함수 반환까지는 0.019076, 0.032323, 0.023276, 0.029323, 0.017565초였다. 이는 출력 직전 Python 코드 실행 시각이며, OS 내부의 순수 프로세스 생성 시간이나 flush 완료 시각 자체를 측정한 것은 아니다.

현재 관측한 첫 실행 시각이 0.4초·0.6초의 시험 준비 예산보다 길며, 1.5초와도 겹친다. 기동 경로의 변동이 관측되었으나, OS 스케줄링·보안 검사·호스트 부하 등 세부 원인을 계측하지 않았으므로 특정 원인으로 단정하지 않는다. 5회 관측은 모든 호스트에서의 최악 기동시간 보증도 아니다.

## 시험 변경 원리

생산 파일 `amdfm/processes.py`는 수정하지 않는다. 변경 전 SHA-256은 `49974870ff83ca05b01d09ca6b55b8593a38ce4c55ab7ca8017083a5fc38180f`이다.

1. 기존 네 시간 민감 사례의 실행 예산을 5초로 명시한다. 이는 첫 Python 실행 약 0.75–1.52초와 추가 자식 인터프리터의 기동을 고려한 시험 설정이며, 제품의 제한 시간을 변경하지 않는다.
2. 제한 시간은 `run_bounded` 호출 시점부터 단 한 번 적용한다. 준비 완료 때 시계를 재시작하거나 예산을 연장하지 않는다.
3. 기존 부모의 Popen 표식 외에 **자식 Python이 직접 쓰는 준비 파일**을 확인한다. 두 준비 표식을 확인하지 못하면 시험은 계속 실패한다.
4. 자식의 위험한 후속 쓰기는 준비 후 6초 뒤로 설정한다. 전체 5초 제한보다 길며, 함수 반환 후에도 6초 기다려 정리되지 않은 자식의 후속 쓰기를 검출한다. 지연 쓰기 검사를 삭제하거나 건너뛰지 않는다.
5. 전체 호출 경과가 `5초 - 0.05초` 이상이고 `5초 + 1.2초` 미만임을 검사한다. 상한의 정리 여유 1.2초는 기존 0.6초 제한/1.8초 상한 시험과 같다. 조기 취소와 준비 후 제한 시간 재시작도 허용하지 않는다.
6. flush 사례도 5초 안에 두 스트림을 flush한 표식을 확인하고, `TimeoutExpired.output` 및 `.stderr` 내용이 원래 기대값과 정확히 같은지 검사한다.

원래 실패 로그는 수정·삭제하지 않는다. 기존 플랫폼 조건부 skip은 그대로이며 새 skip이나 xfail을 추가하지 않는다. 변경한 독립 18개 시험의 실행 결과는 같은 폴더에 별도로 기록한다.

## 보강 후 독립 재시험

실행 명령: `.venv/Scripts/python.exe -m pytest tests_v3/test_processes.py -q --junitxml=validation/machining-2026-09-19/process-timing/process-tests.xml`

결과: **18 passed in 56.22s**. `process-tests.txt`와 `process-tests.xml`에 원출력을 보존했다. 세 자식 정리 사례는 부모 표식뿐 아니라 실제 자식 준비 표식도 확인했고, 시간 제한 예외·전체 호출 상한과 지연 출력 부재를 모두 통과했다. flush 사례도 준비 표식 및 두 예외 출력 스트림의 정확한 내용 보존을 통과했다.

생산 파일의 시험 전후 SHA-256은 동일하다. 이 기록은 변경한 시험 파일의 독립 실행 결과이며, 기존 전체 회귀의 실패를 삭제하거나 전체 회귀 재실행 통과로 바꾸어 표현하지 않는다. 확인한 기동 변동의 세부 원인은 여전히 미확정이다.
