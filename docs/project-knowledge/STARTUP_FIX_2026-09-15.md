# 중복 실행 시 포트 충돌 수정

사용자가 START_REVIEW 실행 시 `Port 8507 is not available` 화면을 보고했다. 확인 당시 바탕화면 AM-DFM_v3_0의 서버 PID 9792가 8507에서 응답했고, `/_stcore/health` 결과는 `ok`였다. 기존 START_REVIEW.cmd가 실행 여부 확인 없이 항상 같은 포트로 새 서버를 시작한 것이 원인이다. 분석 계산의 오류는 아니다.

시작 처리를 표준 라이브러리만 사용하는 `scripts/start_review.py`로 분리했다. Windows의 포트 소유 PID와 명령행 인수를 확인하여 같은 Python 환경과 **절대 경로 app.py**로 실행한 서버이며 상태 응답도 정상인 경우에만 기존 앱을 연다. 일반 HTTP 응답이나 다른 Streamlit의 정상 응답을 이 앱으로 오인하지 않는다. Windows 인수 인식은 CommandLineToArgvW를 사용한다.

새 서버는 절대 앱 경로 및 localhost 주소로 실행한다. 브라우저 열기에 실패해도 정상 서버를 실패로 취급하지 않고 접속 주소를 안내한다. 다른 프로그램이나 실행 폴더를 확인할 수 없는 서버는 종료하지 않으며 `--port`로 다른 포트를 지정할 수 있다. 오류 시 CMD 창을 유지하고 자동 검증용 `--no-pause`, `--no-browser`를 지원한다. 동시에 시작하여 새 서버가 포트 충돌로 종료한 경우 기존 서버의 신원과 상태를 다시 확인한다.

기존 상대 경로 실행은 다른 프로세스의 작업 폴더를 명령행만으로 확인할 수 없어 자동 재사용하지 않는다. 이 수정 배포 시 작업에서 시작한 기존 바탕화면 서버만 확인하여 새 절대 경로 실행으로 재시작한다. 재시작으로 Streamlit 세션은 초기화된다. 계산 엔진, 형상 파일, 기존 검증 결과는 변경하지 않는다.

## 검증

- Windows Python 3.12와 3.13에서 새 시작 검증 23개와 기존 설치 검증 5개를 함께 실행했다. 각 환경에서 28개 모두 통과했다.
- 한글·공백·괄호 폴더의 실제 Streamlit 서버를 임시 포트에 시작했다. 같은 앱을 다시 실행하면 정상 종료 코드 0으로 기존 서버를 재사용했고 서버 PID가 유지됐다. 같은 Python을 쓰는 다른 폴더의 app.py는 정상 상태 응답이 있어도 재사용하지 않았으며 원래 서버 PID와 응답을 보존했다. 두 Python 환경에서 확인했다.
- 첫 Python 3.12 시험에서 Windows venv redirector가 서버 명령행의 실행 파일을 기본 Python 경로로 바꾸는 경우를 발견했다. 현재 가상환경 또는 그 환경의 명시된 기본 Python을 허용하도록 수정하고, 다른 Python과 상대 앱 경로는 계속 거부하는 반례를 추가한 뒤 재시험했다.
- 임시 검증 서버는 그 시험에서 시작한 프로세스 트리만 종료했다. 기존 사용자 서버는 이 시험 중 유지했다. 실제 실행 원본 기록은 저장소 옆 `study/startup-fix-20260915/`와 `study/startup-fix-20260915-py313/`에 있다.

이 수정의 근거는 재현한 Windows 실행 오류와 로컬 Streamlit CLI 문서다. 제조성 문헌의 수치나 판정 기준은 변경하지 않았고, 이전 전체 기하 검증을 이번 수정의 재실행 결과로 표시하지 않는다.
